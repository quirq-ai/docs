## How it works

- **Transport.** Each toolchain is an OCI artifact at
  `ghcr.io/quirq-ai/toolchains/<name>`, addressed by digest. There are no
  containers: each artifact is one tarball layer that `qq sync` unpacks
  without a container runtime.
- **Staging.** A spec change that lands on `main` is built in CI and pushed
  with a `staging-…` tag.
- **Promotion.** A reviewed pull request moves the staged digest into
  [`promoted.toml`](https://github.com/quirq-ai/toolchains/blob/main/promoted.toml).
- **Rolling.** The toolchain roller in [rollers](/docs/qq/rollers) reads
  `promoted.toml` and opens pin-update pull requests in product repos. A
  new repo gets these pins from `qqsync init --promoted`
  ([sync](/docs/qq/sync#start-a-new-repo-qqsync-init)).

## What is promoted

| Toolchain | Version | Built from | Checked with |
|---|---|---|---|
| `python` | CPython 3.14.8 | the python.org source release | xo-space's test suite and route parity check |
| `node` | Node.js 24.21.0 LTS, pnpm 11.28.2 | the official nodejs.org binary and the npm pnpm tarball | innernet's install, typecheck and build |

Each spec, `toolchains/<name>/toolchain.toml`, lists its source URLs and
sha256s, a `build.sh`, smoke tests (for example, the version it reports),
and **consumers**: product repos at a pinned commit that must build with it.

## Add or move a toolchain

1. **Edit the spec.** Change `toolchains/<name>/toolchain.toml` (version,
   source URL, sha256) and `build.sh`. Open a pull request. The `build`
   check builds it, smoke-tests it, and builds its consumers.
2. **Land it.** `build` on `main` stages it as
   `ghcr.io/quirq-ai/toolchains/<name>:staging-…` and prints a ready-made
   record in the run summary. A staged digest is promotable only if that
   run's `consumers` job is green.
3. **Promote it** in its own pull request:

   ```sh
   python tools/qqtc.py promote <name> --record staged.json
   ```

   This rewrites `promoted.toml` in its one canonical form; hand edits are
   refused. The pull request may change only `promoted.toml` and
   `README.md`.
4. **The gate checks it.** `promotion-gate` pulls the digest, checks that a
   staging build of a `main` commit produced exactly those bytes, and
   re-runs the smoke tests and consumer builds. It uses `main`'s tools, not
   the pull request's. A reviewer approves, and it merges through the merge
   queue, where the gate runs again.
5. **The roller** opens pin updates in product repos.

To rebuild the same release after a build-script change, bump `revision`.
To move to a new release, change `version`, the source and its sha256, and
reset `revision` to 1.

## Rules

- Toolchains are referenced only by digest. Never point a consumer at a tag.
- Never promote a digest that CI did not build from this repo.
- Change the gate itself (`.github/`, `tools/`, `toolchains/`) in its own
  pull request. suraj's code-owner review is required on those paths.
- Workflows must declare top-level `permissions` and never grant `checks` or
  `statuses` write (`tools/gate.py check-workflows`).

<Callout type="warn">
  The gate cannot close every way to fake it: anyone with write access can
  push a branch whose workflow posts a green `promotion-gate` check. So the
  roller must re-verify each pin rather than trust `promoted.toml` alone.
</Callout>

**New toolchains start private.** Each new package on ghcr must be made
public by an org admin (suraj) before `qq sync`, recipes and product CI can
pull it. `python` and `node` are public today.
