<Lead>
  The [remote-build repo](https://github.com/quirq-ai/remote-build) defines
  where a build step (an action) runs and how its result is reused. One
  executor interface runs an action on a chosen backend, and an action cache
  skips work already done.
</Lead>

<Callout type="info">
  **Today:** the executor (backends `local` and `github`) and the local
  action cache are merged. Nothing outside this repo calls it yet: `qq
  build`, `qq test` and `qqrecipes execute` run actions on the machine they
  run on. A shared cache is planned for v1; remote execution on Buildbarn
  with autoscaled workers for v2.
</Callout>

## How it works

- **An action** is a [recipes](/docs/qq/recipes) `Action`: a command, an
  input root digest, environment, declared outputs and platform. Its digest
  is its key. A request (`qq-exec-request/1`) adds the files of the input
  root and, for remote backends, the git repository and commit to fetch
  them from. Actions are shaped like REAPI's `Action` and `ActionResult`;
  v0 needs no gRPC.
- **An executor** runs one request and returns the exit code and the digest
  of every output. A non-zero exit code is a result, not an error.
- **Inputs are checked first.** Every executor checks that the files it sees
  hash to the input root digest and that it is on the action's platform. A
  mismatch is a typed error, never a silent run on the wrong inputs.
- **Backends are modules.** `qqrbe.executor.load(backend)` imports
  `qqrbe.backends.<backend>`, so a new backend (`launchpad`, quirq's own
  cloud, or Buildbarn) is one new module.

| Backend | Runs the action |
|---|---|
| `local` | here, through recipes' runner |
| `github` | on a GitHub Actions runner: it dispatches the `execute` workflow, which checks out the commit, verifies the inputs, runs the action and returns the result as an artifact |

The `github` backend needs a token with `actions: write` (`QQ_GITHUB_TOKEN`
or `GITHUB_TOKEN`). v0 uses git as the input store.

## The action cache

- `exec` and `selftest` look the action digest up in `<repo>/.qq/cache`
  first. A hit restores the outputs, log and JUnit and prints `cache: hit`.
  A miss runs the action and stores the result if it succeeded.
- Actions marked `cacheable = false`, or run on a toolchain from `PATH`,
  always run and print `cache: uncacheable`. `--no-cache` turns the cache
  off.

## Fallback

With `--fallback local`, an action the backend cannot run
(`backend-unavailable`, `remote-execution-failed`) runs locally instead.
Every fallback prints a `FALLBACK` line, is marked in the result, and is
counted by backend pair and reason in `.qq/cache/stats.json`. Wrong inputs,
a wrong platform or a bad request never fall back, since they would fail
anywhere.

## Commands

| Command | What it does |
|---|---|
| `qqrbe backends` | list backends (`local`, `github`, ...) |
| `qqrbe selftest --backend local` | run a small deterministic action |
| `qqrbe exec --request req.json --backend github` | run a `qq-exec-request/1` |
| `qqrbe compare local.json github.json` | same action, same output digests? |
| `qqrbe selftest --backend github --fallback local` | fall back to local if GitHub cannot run it |
| `qqrbe stats` | cache hits and misses, fallbacks by reason |

`exec` and `selftest` exit 0 when the action passed, 1 when it did not, and 2 when the executor could not run it (a typed error).

## How CI proves it

- The `cross-backend` job runs `qqrbe selftest` on both backends, and
  `qqrbe compare` fails it unless both give the same action digest and the
  same output digests.
- A second selftest run must be a cache hit.
- A run on `github` with no token must fall back and be counted.
