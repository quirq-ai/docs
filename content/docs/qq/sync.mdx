<Lead>
  Every repo qq builds keeps one manifest, `infra/repo.toml`. It pins the
  repo's qq version, toolchains and dependencies, and lists its targets. The
  [sync repo](https://github.com/quirq-ai/sync) owns its schema and `qqsync`,
  the one library that reads and edits it. Nothing else may parse it.
</Lead>

<Callout type="info">
  **Today:** the schema, the parser and editor, the pin check and the "no
  other parser" guard are all merged. xo-space and innernet carry their own
  `infra/repo.toml`, but sync's presubmit still validates fixture copies of
  them, not the repos' own files.
</Callout>

## What a repo.toml says

In plain words: "this repo has these targets, each of some kind, built with these
pinned toolchains".

```toml
schema = "quirq-repo/1"

[qq]
version = "0.1.0"            # the qq this repo runs

[toolchains.python]          # pinned bytes; the digest is what is checked
version = "3.14.8"
source = "https://..."
digest = "sha256:<64 hex>"

[[targets]]
name = "server"
kind = "python-service"      # names a kind; recipes gives it meaning
srcs = ["server.py", "services/**"]
```

| Part | Who changes it |
|---|---|
| `[qq]` | a product pull request ([how qq picks its version](/docs/qq/cli#how-qq-picks-its-version)) |
| `[toolchains.*]` | the toolchain roller in [rollers](/docs/qq/rollers), through `qqsync` |
| `[[targets]]` | a product pull request: `name`, `kind`, `srcs`, `outs`, `deps`, `cacheable`, `params` |

Unknown keys are errors. Target names are unique, `deps` name targets in the
same file, and there are no cycles. `params` go to the kind's adapter as is.
The full schema is
[`quirq-repo-1.schema.json`](https://github.com/quirq-ai/sync/blob/main/src/qqsync/schema/quirq-repo-1.schema.json).

## Kinds

A `kind` (`python-service`, `pytest`, `node-app`, `gatsby-site`) is just a
name here. It is defined once for the whole org in infra-config's
`config/kinds.toml` and given behavior by an adapter in
[recipes](/docs/qq/recipes#adding-a-kind). sync checks a kind against that
list only when asked (`--kind`); gate always asks. So using an existing kind
is a one-line repo change, while a new kind is an org change first.

## What you do with it

To install `qqsync`, follow [Use qq on your machine](/docs/qq#use-qq-on-your-machine).

```sh
qqsync validate infra/repo.toml               # PASS, or exit 1 with every problem
qqsync validate infra/repo.toml --kind pytest # also require known kinds
qqsync show infra/repo.toml                   # the manifest as JSON
qqsync pins --strict infra/repo.toml          # list pins; reject placeholders
qqsync guard .                                # fail if anything else parses it
```

Other languages call `qqsync show` and read JSON; Python uses
`qqsync.manifest`. Edits are exact: comments and bytes outside the change
stay as they were, and an edit that would make the file invalid is undone.

## Start a new repo

```sh
# one target per kind, the pins those kinds need, and [qq] version
qqsync init . --kind python-service --kind pytest \
  --kinds infra-config/config/kinds.toml \
  --promoted toolchains/promoted.toml \
  --qq-version 0.1.0
qqsync validate infra/repo.toml --kind python-service --kind pytest
```

All four flags are required. It never replaces an existing manifest. New
targets start with no `srcs` and `cacheable = false`; add `srcs`, then
delete that line. Then see [Add a repo](/docs/qq#add-a-repo).

<Accordions>
  <Accordion title="How pins are checked">
    `fetch` downloads to a temporary file, hashes it, and moves it into
    place only when the digest matches; a mismatch stops the build and keeps
    any older good copy. `sha256:` pins check bytes at an `https://` or
    `file://` URL, or a layer of an `oci://...@sha256:<manifest>` source.
    `git:` pins check a commit. Registry packages must be public: no
    credentials are sent.
  </Accordion>
</Accordions>
