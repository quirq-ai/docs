<Lead>
  installer lets a client follow a release channel instead of `main`.
  `qqinstall` reads which commit and artifact digest each channel names, puts

## How it works

The channel manifest is release's `channels.json` (schema `qq-channels/1`)
on its `release-state` branch. Per repo and channel it gives the commit, the
artifact digest and the generation. Only release's executor writes it, after
every channel move.

`qqinstall` refuses the whole file if anything in it is unexpected: the
schema, a 40-hex commit, a `sha256:` digest, a positive generation, no
duplicate keys, at most 1 MiB, https only. The commit always comes from the
manifest, never from the checkout being checked.

The digest is for artifact installs (v1 and v2). A git install is identified
by its commit.

## What you do with it

Install it from a commit you reviewed:

```sh
pip install "qqinstall @ git+https://github.com/quirq-ai/installer@<commit>"
```

Then:

```sh
qqinstall resolve  --repo xo-space --channel canary                 # commit, digest, generation
qqinstall resolve  --repo xo-space --channel canary --format env    # QQ_CHANNEL_COMMIT=... for scripts
qqinstall resolve  --repo xo-space --channel canary --at <release-state commit>   # a fixed read
qqinstall checkout --repo xo-space --channel canary --remote <git URL> --dest ./xo-space   # put an install on it
qqinstall verify   --repo xo-space --channel canary --checkout ./xo-space [--remote <git URL>]
qqinstall show                                                      # every channel
```

### Exit codes

Scripts should decide on the exit code, never on the text.

| Code | Meaning |
|---|---|
| `0` | resolved; for `checkout` and `verify`, the checkout is exactly the channel's commit with no local changes |
| `1` | mismatch or local changes |
| `2` | error: bad manifest, bad arguments, broken checkout or remote, or an older generation |
| `3` | not published yet: no manifest, or it does not name that repo and channel |

Treat anything but `0` as "not verified". Python itself exits `1` if
qqinstall cannot start. website has no canary channel, so it answers `3`.

### What checkout does

- Clones the first time, fetches after that, then detaches at the manifest's
  commit by its id, never by a branch or tag name.
- Refuses a commit that is not on the remote's `--branch` (default `main`),
  so a manifest cannot name an unmerged commit.
- Refuses symlinks to paths outside the commit's tree, and shallow checkouts.
- Removes a first checkout that fails, so the next run starts clean.
- Records the manifest's generation in the checkout's git config and refuses
  (exit `2`) a later `channels.json` with a lower generation. A replayed old
  manifest cannot move an install back. A rollback is a new move with a
  higher generation, so it goes through.

`resolve`, `verify` and `show` keep no state, so they cannot make the
generation check.

## Following canary on a test machine

The rule is check, then run: a test install runs only a checkout `qqinstall`
has already verified. Once, on the test machine (Python 3.11+ and git):

```sh
python3 -m venv ~/.qqinstall && ~/.qqinstall/bin/pip install \
  "qqinstall @ git+https://github.com/quirq-ai/installer@<reviewed installer commit>"
```

Then, from a directory used only for this test install, every time you
install or update:

```sh
~/.qqinstall/bin/qqinstall checkout --repo xo-space --channel canary \
  --remote https://github.com/quirq-ai/xo-space.git --dest ./xo-space \
  && ./xo-space/install.sh
```

Running it again follows promotions and rollbacks alike. Run
`./xo-space/install.sh` from the test directory, not from inside the
checkout. What install.sh downloads afterwards is not verified.

Do not follow canary with `QUIRQ_SOURCE_REF=channels/canary` or the in-app
updaters. They fetch the short name `channels/canary`, which git can resolve
to a planted ref or tag, and they verify nothing.

**If every run exits `2`** because release-state was reset (generations
restart at 1) or a bad manifest raised the record, check what canary
should be, then clear the generation record and run again:

```sh
git -C xo-space config --local --unset-all qqinstall.xo-space/canary.generation
```

## Limits

- `verify` trusts the checkout's own `.git` (filters, excludes,
  `core.fileMode`). It checks an install you control, not a hostile tree. It
  does not check the digest or submodules.
- Reads go through GitHub's CDN and can lag a channel move by a few minutes.
  `--at <release-state commit>` reads a fixed version.
- The trust root is `channels.json` on `release-state`. Until a ruleset lets
  only the release executor App push it (open gate PR #27), anyone with push
  on quirq-ai/release can change what a channel resolves to.
