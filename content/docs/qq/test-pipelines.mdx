<Lead>
  test-pipelines turns test output into stored results and mechanical
  verdicts. It keeps every run's results, will open one failure record for
  each held canary, rollback or auto-revert, and computes the scorecard from what
  it stored, so the numbers come from a script, not a person.
</Lead>

## How it works

| Record | What it is |
|---|---|
| **Result** | one test outcome, write-once, from JUnit XML |
| **Run** | one presubmit, gate or post-submit attempt |
| **Verdict** | pass or fail, computed from Results |
| **Failure** | one per held canary, rollback or auto-revert, mirrored to an issue |

Records use schema `quirq-results/1`. **A missing signal is not a pass:** a
job with no test reports still stores a run, marked as failing.

## Store a job's results

Add the sink after a builder's test steps, pinned by commit:

```yaml
- uses: quirq-ai/test-pipelines/sink@<commit>
  if: always()
  with:
    junit: .qq/out/junit/*.xml
```

It stores the run as an artifact named `qq-results-<run id>`. Failing tests
never fail the sink step.

<Callout type="warn">
  **What you store is public forever.** Each Result keeps only the first 20
  lines and 200 characters of its failure message. Captured output is stored
  only if you pass `keep-raw-junit: "true"`; do that only if everything your
  tests print may be public.
</Callout>

## The results store

The store is a write-once tree on this repo's `results` branch. The
`scorecard` workflow, every 6 hours at :23, collects every `qq-results-*`
artifact into it. Gate's `qq-state-branches` ruleset stops anyone
force-pushing or deleting the branch.

```sh
# check out the store
git fetch origin +refs/heads/results:refs/remotes/origin/results && git worktree add .qq/store refs/remotes/origin/results
# failed post-submit runs of one repo
qqresults query runs --store .qq/store --repo quirq-ai/xo-space --kind postsubmit --failed
# one test's history
qqresults query history --store .qq/store --test 'tests.test_greet::test_hello'
```

## The scorecard

`scorecard.md` and `scorecard.json` sit on the `results` branch. Per repo
they measure gate time to green (p50 and p90), main-red minutes per week,
flake rate, pass rates, runs that stored no results, and failure records.
Nothing unmeasured shows as zero, and the planted demo record is never
counted.

```sh
# last 7 days; add --json for machines
qqresults scorecard --store .qq/store --days 7
```

<Accordions>
  <Accordion title="Retry and failure records (not in any product gate yet)">
    When a builder gives the sink a `rerun` command, failed tests are rerun
    with the change, then on the base commit (values from infra-config's
    `flakes.toml`). A test that passed on a retry is FLAKY, one that failed
    the same way on base is EXONERATED, and anything else is UNEXPECTED and
    blocks. A timeout or crash never exonerates.

    Each held canary, rollback and auto-revert opens one write-once record,
    mirrored to an issue labelled `qq-failure`, through the
    `quirq-ai/test-pipelines/failure` action. A record closes only when its
    culprit, fix and covering test are linked. Security-related and `fuzz`
    records are never mirrored to a public issue. The trust rules are in the
    [README](https://github.com/quirq-ai/test-pipelines/blob/main/README.md).
  </Accordion>
</Accordions>
