qq is not the same as **quirq** the unit of work described in
[quirq: Measure Agent Work](/docs/quirq). It is the build and release system
behind quirq's own repos.

## qq in one minute

- **One config repo decides everything.** `infra-config` lists every repo,
  builder, landing rule and release channel as TOML files. Every tool reads it
  at a pinned commit, so a policy change is a pull request.
- **A product repo writes one file by hand:** its manifest,
  `infra/repo.toml`. CI workflows, repo settings and dependency updates are
  generated from config or delivered by pull request.
- **`qq` is the command line.** It builds and tests a repo the same way on
  every machine, from what the manifest says, so you never need to know the
  repo's language or package manager.
- **It is modelled on Chromium's infrastructure,** rebuilt for small public
  GitHub repos.
- **Who uses it today:** xo-space (Python) and innernet (Next.js) go all the
  way to the daily canary. website (Gatsby) is listed in the config, but is
  not in the canary yet.

## The 13 repos

Each repo does one job. They fall into four stages by where they act on a
change.

| Stage | Repo | Its job |
|---|---|---|
| Your machine | [depot](https://github.com/quirq-ai/depot) | the `qq` command line |
| Your machine | [sync](https://github.com/quirq-ai/sync) | the manifest format and its only reader, `qqsync` |
| Your machine | [recipes](https://github.com/quirq-ai/recipes) | how to build and test each kind of target |
| Your machine | [toolchains](https://github.com/quirq-ai/toolchains) | Python and Node builds, pinned by digest |
| Your machine | [remote-build](https://github.com/quirq-ai/remote-build) | where build steps run, and their cache |
| Before landing | [infra-config](https://github.com/quirq-ai/infra-config) | all policy and builder definitions, as data |
| Before landing | [gate](https://github.com/quirq-ai/gate) | the required checks, repo settings and the merge queue |
| Before landing | [test-pipelines](https://github.com/quirq-ai/test-pipelines) | stored test results, verdicts and failure records |
| After landing | [gardener](https://github.com/quirq-ai/gardener) | keeps `main` green: tree status, finding the culprit, reverts |
| After landing | [rollers](https://github.com/quirq-ai/rollers) | keeps dependencies and toolchains current |
| After landing | [perf](https://github.com/quirq-ai/perf) | performance numbers per commit, as a record |
| Shipping | [release](https://github.com/quirq-ai/release) | `lkgr`, release channels, the daily canary, rollback |
| Shipping | [installer](https://github.com/quirq-ai/installer) | lets clients follow a channel instead of `main` |

Policy flows down from infra-config, results flow back up through
test-pipelines, and every link between repos is a pinned commit, never copied
code.

## How a change travels

Notes marked **Today** say where v0 still stops short.

1. **Set up once.** Install `qq` and `qqsync` (next section).
2. **Get toolchains.** `qq sync` fetches each pinned toolchain, checks its
   digest and links it under `.qq/toolchains/`.
   **Today:** Linux x86_64 only. On a Mac you install the pinned versions
   yourself.
3. **Build and test.** `qq build` and `qq test` run the steps the manifest
   names and write results to `.qq/out`.
4. **Open a pull request.** The repo's generated `<repo>-presubmit` check
   runs: it checks the workflows match config, then installs, builds and
   tests, and stores every test result in test-pipelines.
5. **Ask for a verdict.** `qq try` uploads the branch and returns a run ID at
   once; the verdict comes later. `qq status` shows it on demand.
6. **Land.** `qq land` waits for the gate to pass, then hands the pull request
   to the merge queue, which re-runs the check on the exact merge result and
   squash-merges it.
7. **After it lands.** A post-submit builder runs on every `main` commit.
   gardener publishes whether `main` is open or closed every 5 minutes, and
   when `main` goes red it finds the culprit commit to revert.
   **Today:** gardener cannot open reverts until its GitHub App exists, and no
   revert lands without a person.
8. **Dependencies move.** Dependabot opens update pull requests and rollers'
   `qq-roll-land` check tests them.
   **Today:** a person merges every roll.
9. **Ship.** release moves `lkgr` (last known good) to the newest `main`
   commit whose post-submit builders all passed. Once a day the canary builds,
   tests, deploys and probes `lkgr`, and only then moves the `canary` channel.
   **Today:** the canary shipped both product repos on 2026-10-05. On days
   when `lkgr` has not moved, it records a no-op.
10. **Install from a channel.** `qqinstall resolve --repo xo-space --channel
    canary` gives the commit and digest to install.
11. **Measure.** perf records build size and a benchmark per `main` commit. It
    never blocks a change.

## Use qq on your machine

### What you need

- `git`, and `python3` 3.11.4 or newer with its `venv` module.
- Network access to github.com, PyPI and ghcr.io. No login is needed to build
  and test. `qq try`, `qq land` and `qq status` also need `gh`, logged in.
- Linux x86_64 gets every toolchain fetched for it. On a Mac, `qq sync` stops
  with `no pin for platform …`: install CPython 3.14.8 (xo-space) or Node 24
  with pnpm (innernet) yourself.

Each command below runs inside `( … )`, so your shell and folder stay as they
were, and each is safe to run again. Tools go in `~/qq-tools` and practice
copies in `~/qq-try`; both are safe to delete.

### Install

Install `qq` (prints `qq 0.1.0`):

```sh
( set -e; mkdir -p ~/qq-tools; rm -rf ~/qq-tools/depot; git clone -q https://github.com/quirq-ai/depot ~/qq-tools/depot; ~/qq-tools/depot/bin/qq --version )
```

Install `qqsync` (prints `qqsync 0.1.0`):

```sh
( set -e; mkdir -p ~/qq-tools; rm -rf ~/qq-tools/qqsync; python3 -m venv ~/qq-tools/qqsync; ~/qq-tools/qqsync/bin/pip install -q --disable-pip-version-check "qqsync @ git+https://github.com/quirq-ai/sync@main"; ~/qq-tools/qqsync/bin/qqsync --version )
```

Run both again any time to update. To type `qq` without the full path, add
`~/qq-tools/depot/bin` to your `PATH`.

### The loop

| Step | Command | What it does |
|---|---|---|
| 1. Get the code | `qq fetch https://github.com/quirq-ai/NAME` (Linux) or `git clone` (Mac) | clones; on Linux it also syncs |
| 2. Sync | `qq sync` | fetches pinned toolchains and checks their digests |
| 3. See the targets | `qqsync show infra/repo.toml` | prints the manifest and its targets |
| 4. Build | `qq build [TARGET]` | installs dependencies and builds |
| 5. Test | `qq test [TARGET]` | builds, then tests; results in `.qq/out/results.json` |
| 6. Run | the repo's own start command | there is no `qq run` yet |

On a Mac, add `--toolchain python=ROOT` to `qq build` and `qq test`, where
`ROOT/bin/python3` is the pinned Python. Node apps use the `node` and `pnpm`
on your `PATH`.

For example, on Linux, test xo-space's route parity check (the two settings keep its files inside `~/qq-try`):

```sh
( set -e; mkdir -p ~/qq-try; cd ~/qq-try; rm -rf xo-space; ~/qq-tools/depot/bin/qq fetch https://github.com/quirq-ai/xo-space; cd xo-space; QUIRQ_STATE_ROOT=$HOME/qq-try/state RCLONE_CONFIG=$HOME/qq-try/state/rclone.conf ~/qq-tools/depot/bin/qq test route-parity )
```

Or build and test innernet as the public demo:

```sh
( set -e; mkdir -p ~/qq-try; cd ~/qq-try; rm -rf innernet; ~/qq-tools/depot/bin/qq fetch https://github.com/quirq-ai/innernet; cd innernet; INNERNET_DEMO=1 ~/qq-tools/depot/bin/qq test )
```

### Exit codes

| Command | Exit codes |
|---|---|
| `qq sync`, `qq build`, `qq test` | 0 passed, 1 a step failed, 2 no manifest or a bad one |
| `qq status` | 0 pass, 1 refused, 3 pending |
| `qqsync validate [FILE]` | 0 the manifest is valid, 1 problems listed |

After `qq test`, read `.qq/out/results.json`. Every `FAIL` line names its log
file.

### If something goes wrong

| You see | Do this |
|---|---|
| `no pin for platform macos-arm64` | You are on a Mac: `git clone`, then pass `--toolchain` for Python, or use your own Node 24 |
| `FAIL … toolchain-check` | Install the version the log names (CPython 3.14.8 or Node 24), or run on Linux after `qq sync` |
| `qq: no infra/repo.toml here or above …` | The repo has no manifest yet: add one ([Add a repo](#add-a-repo-to-qq)) |
| A fetch fails behind a proxy | Set `HTTPS_PROXY`; for your own CA, set `SSL_CERT_FILE` and git's `http.sslCAInfo` |

To remove everything:

```sh
( chmod -R u+w ~/.cache/qq 2>/dev/null; rm -rf ~/qq-tools ~/qq-try ~/.cache/qq )
```

## Add a repo to qq

### 1. Give it a manifest

A repo needs one file, `infra/repo.toml`. This one has a single test target:

```toml
schema = "quirq-repo/1"

[qq]
version = "0.1.0"

[[targets]]
name = "tests"
kind = "pytest"
srcs = ["tests/**", "requirements-dev.txt"]
```

Check it with `qqsync validate infra/repo.toml`, then run `qq test`. Pick the
kind that fits:

| The repo is | Kind | It needs |
|---|---|---|
| a Python server or app | `python-service` | `requirements.txt` |
| Python tests | `pytest` | `requirements-dev.txt`, including pytest |
| a Next.js app | `node-app` | `package.json` with a `build` script and a `typecheck` or `test` script, and `pnpm-lock.yaml` |
| a Gatsby site | `gatsby-site` | CI only for now: `qq build` cannot run it locally yet |

Anything else (Go, Rust, a plain npm project) has no kind yet. Change pins only
with `qqsync pin`, and never parse the manifest yourself.

### 2. Put it under qq's landing rules

The repo must be public in quirq-ai. Adding a repo in a language qq already
knows takes pull requests in three repos plus one settings run, with no code
change in any tool:

| Order | Where | Change |
|---|---|---|
| 1 | the new repo | a pull request adding `infra/repo.toml` |
| 2 | infra-config `config/repos.toml` and `config/pipelines.toml` | a `[[repo]]` block, plus a presubmit and a post-submit builder |
| 3 | the new repo | add the workflows from `qqcfg deliver` and rollers' Dependabot files to its pull request, then merge it |
| 4 | gate `settings/github.toml` | a `[[repo]]` entry |
| 5 | an org owner's terminal | the gate apply command, once steps 3 and 4 have merged |
| 6 | GitHub | add the repo to the rollers App installation and turn on Dependabot |

Order matters: gate can only name a repo infra-config already lists, and the
apply only touches a repo whose required check is already on its `main`.

The apply is run by an org owner with `gh` logged in, at the gate commit they
are given. It shows a dry run first, writes only what is approved at its
prompts, and is safe to re-run. The full steps are in gate's
[apply guide](https://github.com/quirq-ai/gate/blob/main/docs/apply-settings.md).

## Who decides what

Every policy is a TOML file in infra-config's `config/` folder, changed by a
pull request. Repo settings are code in gate.

| Policy | File | Today |
|---|---|---|
| Builders per repo | `pipelines.toml` | a presubmit and a post-submit per repo |
| Toolchains and kinds | `kinds.toml` | Python 3.14, Node 24 with pnpm |
| Landing rules | `gate.toml` | squash through the merge queue; which paths need an owner's approval is declared, but owner review is not required on most repos yet |
| Auto-revert limits | `auto_revert.toml` | at most 10 reverts per 24 hours; none land on their own |
| Rolls | `rollers.toml` | Dependabot for pip and npm, weekly toolchain updates |
| Release channels | `channels.toml`, `health.toml` | canary is automatic and daily; dev needs a human owner; stable needs the policy owner |
| Repo rules and merge queue | gate `settings/github.toml` | squash merges through a merge queue; 0 required approvals |

**To change a policy:** edit `config/<area>.toml` and open a pull request (CI
runs `qqcfg validate`). After it merges, deliver any changed workflows with
`qqcfg deliver <repo>` and bump each tool's pin of infra-config so it reads
the change.

**What config cannot loosen:**

- Only the policy owner promotes to stable.
- The canary channel is for agents only.
- Agents may land alone only clean reverts, dependency rolls and docs, and in
  v0 none does.
- At most 10 automatic reverts in any 24 hours.
- Builders that run pull request code get no secrets.
- Repos are public.

**Owners.** suraj owns the org, all 13 infra repos and policy. Review is
advisory today. The other config areas and the product repos have no named
owners yet.

## Where qq stands

qq is built in three versions. v0 is a thin, working version of every repo,
end to end on GitHub. v1 adds an unattended canary, the dev channel, fuzzing
and flake handling. v2 adds remote execution, performance bisection and the
stable channel. v1 and v2 have not started.

v0 is done when all five of these hold at once:

| # | Test | Status |
|---|---|---|
| 1 | All 13 repos public, each with code owners, a generated presubmit and a merge queue | Partly: the infra repos' presubmits are still hand-written |
| 2 | Both product repos gated through shared recipes; a red pull request is refused | Partly: builders run stand-in commands, not recipes |
| 3 | 7 daily canaries in a row with no human touch, a bad canary held, a rollback drill | Not yet: the streak has not started |
| 4 | A planted break reverted automatically | Not started: needs the gardener App |
| 5 | A scorecard computed by a script | Built |

### Limits today

- Fetched toolchains are Linux x86_64 only.
- There is no `qq run`; start an app with its own command.
- Only `qq` 0.1.0 exists, with no release tag.
- CI does not use recipes yet: the generated builders run stand-in commands
  from `kinds.toml`.
- Nothing lands on its own: every revert and roll needs a person.
- GitHub is the only backend.
