<Lead>
  A manifest says *what* a target is (`kind = "pytest"`). The
  [recipes repo](https://github.com/quirq-ai/recipes) says *how* to build and
  test each kind, with one adapter per kind. Adapters are the only place in
  qq allowed to name a language, build tool or test runner. `qq build` and
  `qq test` run through this package.
</Lead>

<Callout type="info">
  **Today:** adapters exist for `python-service`, `pytest` and `node-app`,
  and recipes' own presubmit runs them on xo-space and innernet. Product CI
  does not run them yet: the workflows infra-config generates still run the
  stand-in `interim` commands from `kinds.toml`. That is why a local run can
  differ from CI ([when your result differs](/docs/qq#when-your-result-differs-from-ci)).
</Callout>

## How it works

1. **The manifest lists targets,** each with a `kind`, read through
   [`qqsync`](/docs/qq/sync).
2. **The loader finds the adapter** at `qqrecipes.adapters.<kind with - as _>`.
   A kind with no adapter is `AdapterNotFound`; an adapter that fails to
   import raises, so a broken install never looks like a missing kind.
3. **The adapter turns a target into actions** for the capabilities it has
   (`fetch`, `build`, `test`, `package`, `run`, `deploy`, `bench`, `fuzz`).
   Each action's digest is its cache key, so it can run anywhere, later on
   [remote-build](/docs/qq/remote-build).
4. **Every action leaves JUnit XML** in `.qq/out`, with `results.json`.

| Kind | Capabilities | Toolchain |
|---|---|---|
| `python-service` | fetch, build, run, deploy, bench | python |
| `pytest` | fetch, test | python |
| `node-app` | fetch, build, test, run, deploy, bench | node |

`kinds.toml` also lists `gatsby-site` and `static-docs`, which have no
adapter yet, and `container-image`, planned for later.

## What you do with it

`qq build` and `qq test` call it. To call it directly:

```sh
qqrecipes kinds                                   # adapters and their capabilities
qqrecipes plan test --repo PATH --json            # the actions, without running them
qqrecipes execute test --repo PATH                # run them here; results in .qq/out
qqrecipes check-kinds --infra-config PATH         # adapters agree with kinds.toml?
```

## Adding a kind

A kind is defined once for the org and used by name in each repo's
`infra/repo.toml`. Adding one breaks no existing repo, since none names it
yet. Changing an existing kind affects every repo that uses it. In order:

1. **Declare it** in infra-config's `config/kinds.toml`: its capabilities,
   its toolchain, phase `year-one` (repos may not list later kinds), and the `interim` commands CI runs until recipes does. A
   toolchain a repo tests with needs a property-test library in
   `config/fuzz.toml`.
2. **Add the adapter** as `src/qqrecipes/adapters/<kind>` with an `ADAPTER`
   whose `kind` and `toolchain` match. recipes' presubmit runs
   `check-kinds`, which fails if the adapter is not in `kinds.toml` yet ("add
   it there first") or its capabilities or toolchain differ. A listed kind
   with no adapter is only a note.
3. **A new toolchain** (say Go) is built and promoted in
   [toolchains](/docs/qq/toolchains) first.
4. **Use it** in a repo: list the kind for the repo in infra-config, then
   write `kind = "<new>"` in its manifest. Gate refuses a kind its pinned
   infra-config does not list, so gate's pin moves past step 1 first.
