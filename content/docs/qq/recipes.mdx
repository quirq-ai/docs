<Lead>
  A manifest says *what* a target is (`kind = "pytest"`). The
  [recipes repo](https://github.com/quirq-ai/recipes) says *how* to build and
  test each kind, with one adapter per kind. Adapters are the only place in
  qq allowed to name a language, build tool or test runner. `qq build` and
  `qq test` run through this package.
</Lead>

<Callout type="info">
  **Today:** adapters exist for `python-service`, `pytest` and `node-app`,
  and recipes' own presubmit runs them on xo-space and innernet. Product CI
  does not run them yet: the workflows infra-config generates still run the
  stand-in `interim` commands from `kinds.toml`. That is why a local run can
  differ from CI ([when your result differs](/docs/qq#when-your-result-differs-from-ci)).
</Callout>

## How it works

1. **The manifest lists targets,** each with a `kind`. It is read only
   through [`qqsync`](/docs/qq/sync).
2. **A loader finds the adapter** for the kind:
   `qqrecipes.adapters.<kind with - as _>`. Nothing registers adapters, so a
   new kind is one new module. A kind with no module is `AdapterNotFound`; an
   adapter that fails to import raises, so a broken install never looks like
   a missing kind.
3. **The adapter turns a target into actions.** It implements some of these
   capabilities: `fetch`, `build`, `test`, `package`, `run`, `deploy`,
   `bench`, `fuzz`. One it lacks is a declared state, not an error (a docs
   site has no `test`).
4. **Each action** is shaped like a REAPI `Action`: a command, an input root
   digest (every file the target's and its deps' `srcs` match), environment,
   outputs and toolchain pins. Its digest is the cache key, and the same
   action can run locally, on a GitHub runner, or later on
   [remote-build](/docs/qq/remote-build).
5. **Every action leaves JUnit XML.** A step that writes none (a typecheck, a
   build) gets a one-case report from its exit code. Results land in
   `.qq/out`, with `results.json`.

An action is never cacheable when its toolchain is not pinned by a real
digest, or when it used the tool on `PATH`. A `srcs` glob that matches no
file is an error.

## Adapters

| Kind | Capabilities | Toolchain | What it runs |
|---|---|---|---|
| `python-service` | fetch, build, run, deploy, bench | python | a venv in `.qq/venv`; build byte-compiles `srcs`; run and deploy start `params.entry` on `$PORT` |
| `pytest` | fetch, test | python | installs `requirements-dev.txt`; JUnit to `{out}/junit/<target>.pytest.xml` |
| `node-app` | fetch, build, test, run, deploy, bench | node (bundles pnpm) | `pnpm install --frozen-lockfile`; the `build` script; test runs `typecheck` (or `tsc --noEmit`), then vitest or the `test` script; run and deploy use `next start` |

infra-config's `kinds.toml` also lists `gatsby-site`, `static-docs` and
`container-image`, which have no adapter yet. Each adapter's docstring lists
its `params`.

**Property tests.** Hypothesis (Python) and fast-check (TypeScript) tests run
inside `test`, deterministic and time-boxed: 100 examples each, and for
fast-check seed 42 and 5 s per property. `QQ_PROPERTY_*` variables override
the bounds and so change the action key.

**Deploy.** `qqrecipes execute deploy` builds each target, starts it on a
free port in the canary test environment, waits until its ready path
answers below HTTP 500, runs its HTTP probes (below 400 passes), and always
tears it down. v0's only backend is `local`; on GitHub that is the Actions
runner. **Bench** times start-up or GET latency and writes samples to
`{out}/bench/` for [perf](/docs/qq/perf).

## What you do with it

Most people use it through `qq build` and `qq test` ([the command
line](/docs/qq/cli)). To call it directly:

| Command | What it does |
|---|---|
| `qqrecipes kinds` | adapters and their capabilities |
| `qqrecipes plan test --repo PATH [--json]` | the actions, without running them |
| `qqrecipes execute test --repo PATH [--toolchain python=ROOT]` | run them here; results in `.qq/out` |
| `qqrecipes check-kinds --infra-config PATH` | check the adapters agree with `kinds.toml` |

`execute` also takes `--target`, `--out`, `--keep-going` and `--backend`. It
exits 0 when every action passed and 1 when one failed or the manifest or
plan is invalid.

A target in `infra/repo.toml` looks like this (from the repo's
`examples/python-service`):

```toml
[[targets]]
name = "server"
kind = "python-service"
srcs = ["server.py", "greet.py", "requirements.txt"]
params = { ready_path = "/health", probes = ["/health", "/greet?name=qq"] }
```

## Adding a kind

Add one module under `src/qqrecipes/adapters/` with an `ADAPTER` whose
`kind` and `toolchain` match infra-config's `kinds.toml`, and one method per
capability. CI checks that every adapter implements exactly the
capabilities `kinds.toml` lists, and `tools/agnostic_guard.py` fails if any
other module names a language or tool.
