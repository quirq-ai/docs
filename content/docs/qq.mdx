<Lead>
  qq (quirq infra) is how quirq builds, tests and lands code, and how it will
  ship it. You write code as usual, human or agent. qq decides whether it
  lands, keeps `main` green and moves tested commits into release channels.
  Today the only channel is the daily canary, for agents and test
  environments. Users still install from `main`.
</Lead>

<Callout type="info">
  To use qq, read the first three sections. qq is not **quirq**, the
  [proposed unit for agent work](/docs/quirq).
</Callout>

## The idea

- **One config repo decides everything.** `infra-config` holds every policy
  as TOML; changing one is a pull request there.
- **A product repo writes one file by hand,** `infra/repo.toml`. Its CI is generated
  from config, and its GitHub settings are applied from the `gate` repo.
- **`qq` is the command line.** It builds and tests any repo the same way.
- **Who uses it:** xo-space and innernet, all the way to the canary. website
  is listed but not in the canary.

**Words used below**

- **v0:** the first, thin version of qq, being finished now.
- **Pinned by digest:** named by the hash of its exact bytes, so every
  machine that fetches it gets the same bytes.
- **Presubmit:** the blocking check on a pull request.
- **Merge queue:** tests each pull request merged onto the latest `main`
  before it lands.
- **Post-submit:** the builder that runs on `main` after a change lands.
- **lkgr** (last known good): the newest `main` commit whose post-submit
  builders all passed.
- **Canary:** the daily release channel, built from lkgr; dev and stable come
  later.

## How a change moves

1. **Build and test locally** with `qq build` and `qq test`.
2. **Open a pull request.** The presubmit checks the generated workflows were
   not hand-edited, then installs, builds, tests and stores the results.
3. **Land.** `qq land` waits for a pass, then hands the pull request to the
   merge queue.
4. **Watch `main`.** The `gardener` repo reports every 5 minutes whether
   `main` is green and narrows a failure to suspect commits. **Today:** it
   only reports until its GitHub App exists; no revert lands without a person.
5. **Ship to canary.** The `release` repo moves lkgr. Once a day the canary
   builds lkgr, starts it on a CI runner, probes it, then moves the canary
   channel. **Today:** GitHub often skips scheduled runs here, so a daily
   backstop routine (07:37 UTC), run outside these repos, starts any missed
   lkgr or canary run. The first canary, started by hand on 2026-10-05,
   shipped both products. lkgr and the channel are recorded only in
   release's `release-state` branch.
6. **Install from a channel.** `qqinstall` names a channel's commit and
   digest. **Today:** every install, including xo-space's `install.sh` and
   in-app updater, follows `main`; canary test machines are not set up yet.

Dependency updates come from Dependabot; today a person merges each one.

## Use qq on your machine

You need `git` and `python3` 3.11.4 or newer with its venv module
(Debian/Ubuntu: `python3-venv`). Toolchains are fetched for
Linux x86_64 only. On a Mac, `qq sync` stops with `no pin for platform`, and
you install the pinned Python 3.14.8 or Node 24 yourself.

Each command runs inside `( … )`, so it leaves your shell as it was, and each
is safe to run again. Install `qq` and `qqsync`, then put both on your `PATH`
(it adds one line to `~/.bashrc` for bash, to `~/.zshrc` otherwise, and on a Mac
to the first of `~/.bash_profile`, `~/.bash_login` or `~/.profile` that bash
already reads; open a new terminal afterwards):

```sh
( set -e; mkdir -p ~/qq-tools; rm -rf ~/qq-tools/depot; git clone -q https://github.com/quirq-ai/qq ~/qq-tools/depot; ~/qq-tools/depot/bin/qq --version )
```

```sh
( set -e; mkdir -p ~/qq-tools; rm -rf ~/qq-tools/qqsync; python3 -m venv ~/qq-tools/qqsync; ~/qq-tools/qqsync/bin/pip install -q --disable-pip-version-check "qqsync @ git+https://github.com/quirq-ai/sync@9f4c77ebe2c81d6ffd643d737a35b962f6fd322a"; ~/qq-tools/qqsync/bin/qqsync --version )
```

```sh
( case "$SHELL:$(uname)" in */bash:Darwin) for rc in ~/.bash_profile ~/.bash_login ~/.profile ~/.bash_profile; do [ -f "$rc" ] && break; done ;; */bash:*) rc=~/.bashrc ;; *) rc=~/.zshrc ;; esac; mkdir -p ~/qq-tools/bin && ln -sf ~/qq-tools/depot/bin/qq ~/qq-tools/qqsync/bin/qqsync ~/qq-tools/bin/ && { grep -qs 'qq-tools/bin:' "$rc" || printf '\nexport PATH="$HOME/qq-tools/bin:$PATH"\n' >> "$rc"; } && echo "qq-tools/bin is on PATH in $rc; open a new terminal" )
```

The first two print `qq 0.1.0` and `qqsync 0.1.0`. qqsync is pinned to the
sync commit that qq itself pins in its `pyproject.toml` as of 2026-10-07,
so the two agree. Then, in any repo that
has `infra/repo.toml`:

{/* Same sync commit as quirq-ai/qq pyproject.toml:15 (and recipes pyproject.toml); bump them together, with setup's cli/tools.mjs and its fixture. */}

| Command | What it does |
|---|---|
| `qq fetch https://github.com/quirq-ai/NAME` | clone and sync (Linux; on a Mac use `git clone`) |
| `qq sync` | fetch the pinned toolchains and check their digests |
| `qqsync show infra/repo.toml` | list the repo's targets |
| `qq build [TARGET]` | install dependencies and build |
| `qq test [TARGET]` | build and test; results in `.qq/out/results.json` |
| `qq run "COMMAND"` | run a command once, from the repo root, with the pinned toolchains first on `PATH` |
| `qq create NAME COMMAND` | give the repo a command of its own, saved as `infra/commands/NAME.sh` |
| `qq NAME [ARG ...]` | run that command, like any other qq command |

`qq run` starts an app with the toolchains `qq sync` fetched. For example, on
Linux:

```sh
( set -e; mkdir -p ~/qq-try; cd ~/qq-try; rm -rf innernet; qq fetch https://github.com/quirq-ai/innernet; cd innernet; INNERNET_DEMO=1 qq test; qq run "pnpm start" )
```

That serves innernet at **http://127.0.0.1:3470**. **Ctrl-C** stops it. If `qq run`
says `invalid choice: 'run'`, run the first install command again. On a Mac, `qq run` uses the tools on your `PATH` and
names the pinned toolchains it could not use.

### Add your own commands

`qq create` gives a repo a command of its own, and `qq NAME` runs it like any
other qq command:

```sh
qq create check ./scripts/check --all
qq check --fast
```

The first saves `infra/commands/check.sh`; the second runs
`./scripts/check --all --fast`.

- **Share it** by committing `infra/commands/NAME.sh`; teammates and agents
  then get `qq NAME` too. `qq --help` lists the repo's commands under qq's own.
- **It runs like `qq run`:** from the repo root, with the pinned toolchains
  first on `PATH`.
- **Arguments.** Created from several words, each word stays one word and the
  arguments you give `qq NAME` are passed on after them. Created from one
  argument (a quoted command line, or a single word such as
  `qq create lint ruff`), it is saved as typed: add `"$@"` where arguments go,
  or qq refuses to run it with arguments rather than drop them. `qq NAME --help`
  shows the command when it takes no arguments; otherwise `--help` goes to the
  command.
- **Names** are lowercase letters, digits, `-` and `_`. qq's own command names,
  and names one typo away from them (`snyc`, `tets`), cannot be created, so a
  mistyped `qq sync` never runs a repo's code. `qq create --force NAME COMMAND`
  replaces a command.
- **Trust.** A repo's command is code in that repo, and CI does not run it.
  Before running one from a repo you do not trust, read it with `less` or
  `cat -v` (plain `cat` lets terminal escapes in it act).

### When your result differs from CI

A pass on your machine does not yet guarantee a pass in a presubmit, because the
two do not run the same thing:

- **Different commands.** `qq build` and `qq test` run qq's own build steps for
  each kind of repo (the recipes). CI still runs simpler stand-in commands from
  infra-config's
  [`kinds.toml`](https://github.com/quirq-ai/infra-config/blob/main/config/kinds.toml),
  for example `pnpm install --frozen-lockfile`, `pnpm build` and
  `pnpm typecheck` for a Next.js app.
- **Different tool versions.** On Linux x86_64, `qq sync` gives you CPython
  3.14.8, Node 24.21.0 and pnpm 11.28.2. CI sets up Python 3.14 and Node 24
  with GitHub's setup actions and installs pnpm 10, so Python and Node may be a
  slightly different release, and pnpm is a different major version (11
  locally, 10 in CI).

Until that changes, the presubmit on your pull request is the result that
counts. When the two disagree, open the presubmit's log to see which step
failed, then run CI's commands yourself. After `qq sync`, in a Next.js repo:

```sh
qq run "set -e; npx -y pnpm@10 install --frozen-lockfile; npx -y pnpm@10 build; npx -y pnpm@10 typecheck"
```

and in xo-space (pip installs into a fresh virtualenv in your home folder, never
into the shared toolchain):

```sh
qq run 'set -e; rm -rf ~/qq-ci-venv; python3 -m venv ~/qq-ci-venv; . ~/qq-ci-venv/bin/activate; python -m pip install -q --disable-pip-version-check -r requirements.txt; python -m pip install -q --disable-pip-version-check -r requirements-dev.txt; python -m compileall -q .; python -m pytest -q -p no:cacheprovider'
```

On a Mac, `qq run` uses the tools on your `PATH`: in the xo-space command, write
`python3.14` in place of `python3`.

Moving CI onto the recipes is open v0 work (the second row under
[Where qq stands](#where-qq-stands)). Moving CI onto the toolchains `qq sync`
fetches is planned for v1.

<Accordions>
  <Accordion title="Exit codes and common errors">

`qq sync`, `qq build` and `qq test` exit 0 when everything passed, 1 when a
step failed, and 2 when `infra/repo.toml` is missing or invalid. Every `FAIL` line
names its log file.

`qq run` and `qq NAME` exit with the command's own code. When qq itself fails
they exit 125: `qq run` with nothing to run or outside a repo, or a command file
qq cannot read or refuses to run. A command that is not found gives 127, and one
that cannot run gives 126. A name the repo has no command for is an unknown qq
command and exits 2. `qq create` exits 2 on bad usage or outside a repo, and 1
when it cannot create the command (the name is taken, the file exists).

| You see | Do this |
|---|---|
| `no pin for platform macos-arm64` | Install the pinned version yourself and pass `--toolchain python=ROOT` to `qq build` and `qq test`; for Node, put Node 24 and pnpm on `PATH` |
| `FAIL … toolchain-check` | Install the version the log names, or run on Linux after `qq sync` |
| `qq: no infra/repo.toml here or above` | The repo has no manifest yet ([Add a repo](#add-a-repo)) |
| `Could not find a production build in the '.next' directory` | Run `qq test` before `qq run "pnpm start"` |
| `qq NAME never mentions its arguments` | Add `"$@"` where the arguments go in `infra/commands/NAME.sh` |
| `NAME is one typo away from qq …` | Pick another name, or rename the file |

  </Accordion>
  <Accordion title="Send a change for review with qq">

These need `gh` logged in. `qq try` pushes the branch, opens or updates its
pull request and returns at once. `qq status` prints the verdict: 0 pass,
1 refused, 2 error, 3 pending. `qq land` lands it through the merge queue once
the verdict is a pass.

## Add a repo

The repo must be public in quirq-ai. First give it `infra/repo.toml`:

```toml
schema = "quirq-repo/1"

[qq]
version = "0.1.0"

[[targets]]
name = "tests"
kind = "pytest"
srcs = ["tests/**", "requirements-dev.txt"]
```

Check it with `qqsync validate infra/repo.toml`, then `qq test`. The kinds
are `python-service` (needs `requirements.txt`), `pytest` (needs
`requirements-dev.txt`), `node-app` (a Next.js app with pnpm) and
`gatsby-site` (CI only: `qq build` cannot run it locally yet). Other languages
have no kind yet.

Then put it under qq's landing rules, in this order:

1. **The new repo:** a pull request adding `infra/repo.toml`.
2. **infra-config:** add the repo to `config/repos.toml`, with a presubmit
   and a post-submit builder in `config/pipelines.toml`.
3. **The new repo:** in infra-config, run
   `python3 tools/qqcfg.py deliver <repo> <path to its checkout>`, add the
   generated workflows to the step 1 pull request, and merge it.
4. **gate:** add a `[[repo]]` entry to `settings/github.toml`, and move the
   infra-config commit in `pins.toml` to one that lists the repo.
5. **An org owner** applies the settings at the gate commit they are given.
   It shows a dry run and writes only what is approved at its prompts:

```sh
( mkdir -p ~/qq-apply && cd ~/qq-apply && rm -rf qq-gate && git clone -q https://github.com/quirq-ai/gate qq-gate && cd ./qq-gate && git checkout -q <COMMIT> && scripts/apply.sh )
```

Release does not act as its executor App yet. Once it does, every repo it
lists needs the App installed, or release's lkgr job fails for every repo. So
install the release executor App on the repo and add the repo to gate's
`executor_repos` before release moves its infra-config pin past this change. Dependency rolls
(Dependabot and the rollers App) are optional and can come later.

## Who decides what

Every policy is a TOML file in infra-config's `config/` folder (builders,
toolchains, landing rules, revert limits, rolls, channels). To change one,
open a pull request there; after it merges, deliver changed workflows as in
step 3 above and move each tool's infra-config pin. Config cannot loosen
these rules:

- Only the policy owner (suraj) promotes to stable.
- The canary is for agents only.
- Agents may land alone only clean reverts, dependency rolls and docs. In v0,
  none does.
- Gardener creates at most 10 reverts, proposed or landed, in any 24 hours.
- Builders that run pull request code get no secrets.
- Repos are public.

suraj owns the org, the 13 infra repos and policy. Review is advisory: no
approvals are required, except suraj's code-owner review on toolchains' build
and promotion paths.

## Where qq stands

v0's goal is a thin, working version of every repo, end to end on GitHub.
Its code is built. Its GitHub settings were last applied at gate `6610664`, which
covered the 13 infra repos plus xo-space and innernet. Gate #23, #24, #25, #26
and #28 (website onboarding) are merged but not applied yet, and the
release-state rules are in gate #27, which is still open. Its exit
test has not passed. v1 (automatic canary rollback, the dev channel, fuzzing)
and v2 (remote execution, the stable channel) come after. The exit test, as of
2026-10-07:

| Test | Status |
|---|---|
| Generated presubmits and merge queues on every repo | Partly: infra repos' presubmits are hand-written |
| Products gated through recipes; a red pull request refused | Partly: stand-in commands; no refusal recorded |
| 7 unattended daily canaries, a held canary, a rollback drill | Not yet |
| A planted break reverted automatically | Not started: needs the gardener App |
| A scorecard computed by a script | Built |

**Limits today:** Linux x86_64 toolchains only; no `qq` release tag; CI does
not run a repo's own commands; nothing lands on its own; scheduled jobs run late, so lkgr, perf
and the canary lag (perf has not recorded since 2026-10-05).
