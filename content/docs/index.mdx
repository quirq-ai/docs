# What is qq

<Lead>
  qq is quirq's build and release infrastructure, and `qq` is its command
  line. You write code the way you always do, by hand or with an agent. qq
  builds and tests it the same way on your laptop and on GitHub, decides
  whether it may land, keeps `main` green, and moves tested commits out to
  a release channel.
</Lead>

## What qq does for you

- **The same tools on every machine.** Each repo pins its toolchains (Python,
  or Node with pnpm) by the hash of their exact bytes, and `qq sync` fetches
  exactly those bytes, so you and your teammates build with the same tools.
- **One file per repo.** A repo describes itself in `infra/repo.toml`: its
  targets and the toolchains they need. Its CI workflows are generated for
  it. Nobody hand-writes CI.
- **A gate that cannot be talked around.** A change lands only through the
  merge queue, after its required checks pass on the exact merge result.
  The rules live in one config repo, so they are the same for people and
  for agents.
- **Main stays green, and good commits ship.** After a change lands, qq
  watches `main`, records the newest all-green commit, and once a day
  builds, starts and probes it before moving the canary channel to it.

## The life of a change

This is the whole journey. Each step links to the guide for it.

1. **Get the tools.** [Install](/docs/install) `qq` and `qqsync` once.
2. **Build and test locally.** `qq test` builds every target with the
   repo's pinned toolchains and tests it ([your first build](/docs/first-build)).
3. **Send it for review.** `qq try` pushes your branch, opens the pull request
   and returns at once. The presubmit check runs on GitHub
   ([send a change](/docs/send-a-change)).
4. **Land it.** `qq land` waits for the gate to pass, then hands the pull
   request to the merge queue, which tests it on top of the latest `main`.
5. **After it lands.** A post-submit build runs on the new `main` commit. qq
   reports whether `main` is green, moves lkgr (last known good) forward, and
   ships lkgr to the daily canary ([after it lands](/docs/after-it-lands)).

<Callout type="info">
  **Today:** qq is an alpha (version `0.1.0`). Its pinned toolchains exist
  for Linux x86_64 only. xo-space and innernet go all the way to the canary;
  website is behind the gate but not in the canary. Product CI still runs
  simpler stand-in commands, so [a local result can differ from
  CI](/docs/build-test-run#when-your-result-differs-from-ci). What is built
  and what is next: the [roadmap](/docs/roadmap).
</Callout>

## Common questions

<Accordions>
	<Accordion title="Can I use qq on a Mac?">
		Yes, with your own tools. qq itself runs anywhere with `git` and Python
		3.11.4 or newer. The pinned toolchains are published for Linux x86_64 only,
		so on a Mac `qq sync` stops with `no pin for platform`. Clone with `git
		clone`, install Python 3.14.8 or Node 24 yourself, and pass it to `qq
		build` and `qq test` with `--toolchain`. See [Install qq](/docs/install#on-a-mac).
	</Accordion>
	<Accordion title="Do I have to use qq to contribute?">
		No. A plain `git push` and a pull request go through the same gate. qq
		makes the local loop match CI and lets an agent send a change without
		holding a terminal open while CI runs.
	</Accordion>
	<Accordion title="Who decides the rules?">
		Every policy is a TOML file in the
		[infra-config](/docs/infrastructure#infra-config) repo. Changing one is a
		pull request there. A few rules cannot be loosened by config at all, for
		example that only clean reverts, dependency rolls and docs may ever land
		without a person.
	</Accordion>
	<Accordion title="Where are the XO Space docs?">
		XO Space, XO Cloud and their agents are documented at
		[docs.xo.builders](https://docs.xo.builders). This site is only about qq.
	</Accordion>
</Accordions>
